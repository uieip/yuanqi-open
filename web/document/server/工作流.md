# 一、工作流引擎原理
工作流引擎的工作原理可以简单概括为以下几个步骤。
1. 流程定义
用户通过工作流引擎提供的流程定义工具，定义业务流程中的各种节点和转移条件，以及与之相关的任务分配、审批和通知规则等。
2. 流程运行
当业务数据进入工作流引擎时，引擎会根据预定义的流程模板，自动将业务数据分配给相应的处理者，并自动执行流程中的各个环节，直至业务流程结束。在执行流程过程中，工作流引擎会自动记录和管理各种数据和状态信息，以支持后续的流程跟踪和监控。
3. 任务管理
当流程中需要人工处理的任务时，工作流引擎会根据预定义的任务分配规则，自动将任务分配给相应的处理者，并等待处理者完成任务后继续流程执行。在任务执行过程中，工作流引擎会提供相应的界面和工具，以支持任务处理者的任务处理和反馈。
4. 数据管理
在流程执行过程中，工作流引擎会自动记录和管理各种数据和状态信息，以支持后续的流程跟踪和监控。同时，工作流引擎还可以提供数据访问接口，以支持业务系统对流程数据的查询和修改操作。
5. 通知管理
在流程执行过程中，工作流引擎会根据预定义的通知规则，自动向相关人员发送通知，以支持业务流程的实时协同和沟通。
6. 安全管理
在流程执行过程中，工作流引擎会根据预定义的安全规则，限制不同用户对流程数据和操作的访问权限，以确保流程的安全性和可控性。

工作流引擎的核心原理是基于状态机和事件驱动的编程思想，将业务流程中的每个步骤和任务定义为不同的状态，然后通过事件的触发来驱动状态之间的转换。当一个任务完成后，它会触发事件，该事件将引发下一个任务的执行。
另外，工作流引擎还支持审批和流程管理，它能够监控工作流程的进展状态，识别潜在的问题，并在必要时提供通知和警报。工作流引擎还可以自动化分配任务，分配权重和优先级，允许更快的决策和协调。

要实现工作流引擎，需要考虑以下几个因素：
- 1)流程建模：定义流程中的每个步骤和任务，包括输入和输出、预期时间和成本。
- 2)执行引擎：负责执行流程和任务，包括处理异常和错误。
- 3)管理界面：提供用户界面，使用户可以管理进展状态、审批流程和任务分配。
- 4)通信接口：与其他系统通信，以便将工作流引擎集成到现有业务逻辑中。
- 5)数据存储：存储工作流程和任务的状态和结果，以便进行分析和优化。

# 二、工作流引擎架构
流程通过点、线表示，点表示节点，线表示转移路径（条件）。
-点的类型包括：
    - Start：开始节点，用于启动流程。
    - Return：退回节点，用于退回流程。
    - Exec：执行节点，用于执行业务逻辑。
    - Judge：判断节点，用于判断是否满足条件。
    - Proc：程序节点，用于执行程序逻辑。
    - End：结束节点，用于结束流程。
    - Cancle：取消节点，用于取消流程。
    - Comment：描述节点，用于添加注释。
- 线的类型包括：
    - Normal：普通线，用于表示节点之间的普通转移路径。
    - Conditional：条件线，用于表示节点之间的条件转移路径。

## 流程初始化
``` javascript
/*
    init_data:流程初始化参数
    callback:回调
    is_test:测试，默认：否
*/
wfInit: function (init_data: Record<string, any>, callback: (data: Record<string, any>) => void, is_test: boolean) 
```
init_data
``` json
{
    verId:"111111",   //流程版本id
    case_when:"",     //流程过滤条件
    params:{   //初始化数据设置
        name1:"value1",
        name2:"value2"
    },
    parameter:{   //执行人输入参数
        user_id:"value1",
        org_id:"value2",
        other1:"1"
    },
    wfName:"我的流程",
    topic:"测试数据",
    dbName:"yqbase",
    tbName:"a_test_m",
    tbId:"sid1111-1-1" //表记录id
}
```

callback 回调参数
``` json
{
    "error": 0,          //0-成功，9-失败
    "info": "success",   //说明，失败时为错误信息
    "wf": {},            //初始化后的流程数据
    "users": ["1"],      //参与人id列表（发起人）
    "sid": "1111-111-111",         //流程实例id，仅执行模式返回
    "row": {},                     //wf_info 主表行数据，仅执行模式返回
    "stamp": "2025-01-25 08:50:01" //时间戳，仅执行模式返回；客户端写入 wf.info.stamp
}
```

### 初始化（wfInit）
- info：wfstate=0（初始化）；写入 s_time（发起时间）；删除 e_time；测试模式删除 submit 数组
- info 补充：wfname、topic、db_name、tb_name、tb_id 取自 init_data
- node：class=1/2（开始/退回）users=[发起人]；class=5（执行）按 roleType/roleMark 计算 users（测试模式按 duplicateType 生成测试用户：2-最小通过人数、3-最小通过百分比 为 3 人，4-全部通过 为 2 人，其余 1 人）；开始节点 todo=1（待办）、s_time=当前时间
- link：测试模式删除全部 todo

### 提交（wfSubmit）
1. 审批人回填：当前节点 users 中匹配且未审批（mmdId 为空）的执行人写入 mmdId（操作类型）、e_time；代审（执行人≠审批人）时追加 checkin、checkin_name（测试仅 checkin）
2. 提交记录：submit.user.id==self 时删除 self；写入 time（提交时间）；info.onNum 存在时带入 onNum（退回次数）；push 到 data.submit
3. 节点裁决：按 duplicateType（1-单人 2-最小通过人数 3-最小通过百分比 4-全部通过）汇总各执行人 mmdId（1-同意 2-重新提交 0-退回 8-取消）得出节点 mmdId；未达成条件（mmdId=-1）时直接返回，流程停留当前节点等待其余执行人
4. 达成后：当前节点 todo=9（完成）、e_time；info.params 更新为出线计算结果；mmdId=2（退回）时 info.onNum+1（首次记 2）
5. 线处理：经过的线 todo=9；info.wfstate 已为 8（取消）/9（结束）时停止后续流转
6. 节点处理（按 class）：
    - 1/2/5 开始/退回/执行：todo=1、s_time=当前时间；info.wfstate=节点 class；清除其后节点与线的运行状态（node.todo、s_time、e_time，users 的 mmdId、e_time、checkin，link.todo；终点为开始/退回节点的线保留状态）；class=5/6/7 做递归检测，存在递归返回 error=9
    - 6 判断：todo=9；info.wfstate=5；按出线 expression 计算走向继续流转
    - 7 程序：todo=9；info.wfstate=5；测试默认按同意（mmdId=1）计算出线继续流转
    - 8/9 取消/结束：todo=9；info.wfstate=节点 class；info.e_time=当前时间，流程终止
7. 服务端差异：待办/已办/业务表状态等落库动作以 data_todo 收集（todo:add、todo:end、comp:add、tb:state、info:state、tb:wflock），随提交一并写入；运行状态先写 info._wfstate，提交成功后再落回 info.wfstate

### 更新执行人（wfUppUser）
- node.key 匹配节点：roleIsEdit=true，users 整体替换
- 本地（localUppUser）仅回传处理后的流程数据本身；服务端写回 wf_json 并返回新 stamp
